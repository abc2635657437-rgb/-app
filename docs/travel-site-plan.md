# 同路人：从「旅行 App 雏形」到「真正的旅行网站」

> 2026-10-21 · 基于线上 https://travel-world-mwdw.onrender.com 与当前代码实测

## 一、体检结果（都是实测，不是感觉）

| 维度 | 现状 | 意味着什么 |
| --- | --- | --- |
| 内容资产 | 1000 个目的地、195 个国家；约 712 个有可用照片；14 条路线；1 篇做了来源核对的深度路书；100 个地标 | 有骨架，缺血肉 |
| 中文内容 | 目的地目录里 **0 条中文介绍**；长城详情页原文是「暂无可靠来源的中文介绍」 | 最要命的短板：用户搜到也留不住 |
| 可发现性 | `sitemap.xml` 只有 **1 条 URL**；内容全在单页 SPA 里；探索页 **0 个 `<a href>`**；点开地点 URL 不变；`document.title` 全程不更新；只有 WebSite 一条结构化数据 | 搜索引擎几乎没有可抓取、可排名的页面 |
| 社区 | 公开 feed 只有 8 条内测帖；`/api/routes` 返回 0；互动为 0 | 社区还没开张，不要假装热闹 |
| 性能 | 首页 **5.3 MB / 77 请求**；探索页 **9.1 MB / 103 请求**；LCP 约 3.7s（无节流桌面） | 移动端首屏会很慢，直接损失留存 |
| 浪费 | 线上仍会下载 2.97 MB 的 `page-bg-great-wall-mobile.png`（CSS 已隐藏）；1.84 MB 的 `ai-travel-companion.png` 只用作 48px 头像 | 每页白花 ~4.8 MB |
| 基础设施 | Render **free** 计划（会休眠）；Cloudflare 在前提速；无统计、无监控 | 第一次访问可能等几十秒；也不知道用户从哪来 |
| 信任 | 隐私、条款页存在；缺 about / contact / 编辑方针；AI 图有明确标注（这点做得对） | 有「不编造」的底线，但缺「谁在写、怎么核对」的说明 |
| 商业化 | 订座/门票/住宿链接只出现在 AI 行程卡片里；没有邮件订阅 | 内容不产生收入，也不沉淀用户 |

**一句话诊断**：现在是一个功能齐全（地图、AI 行程、社区、同行、聊天）的旅行 App 雏形；还不是一个「旅行网站」，因为缺三件事——**可被搜到的页面、值得信任的内容、能转化的路径**。

## 二、六条改进建议

### 1. 定位收窄：先把 20 个目的地做透，再谈全球 1000

- 不要用「1000 个目的地」当卖点，用户感受不到；先用 3 条走廊做样板：**日本 · 泰国 · 欧洲经典**（或你熟悉的线路）。
- 选择标准：有搜索量、有直飞、你亲自去过、能拿到授权照片。每个目的地先做 **1 个能排名、能照着走、能订** 的页面。
- 1000 个目录页先只做「索引」，不急着让它们全部进搜索结果——薄页面反而会拖累整站。

### 2. 内容：把「相册 + 占位」变成「可执行指南」

每个目的地页固定六段（正好对应现有的 吃·喝·玩·乐·住·行）：

- 开头 300–600 字中文：这是什么地方、适合谁、几月去、待几天、要花多少钱；
- 每段 2 个具体条目：名字、位置、为什么推荐、注意事项；
- 2 张以上授权照片（保留作者/许可/来源，现有能力已经有）；
- 交通：机场/火车站到市区、当地移动方式、常见票价；
- 费用：区间而不是「最低价」，标注核价日期；
- 页脚：资料来源、最后更新时间、作者/编辑。

落地方法：

- 先补 **Top 50**（长城、故宫、西湖、富士山、清水寺、曼谷大皇宫……），宁缺毋滥；
- 供稿用 Wikipedia/Wikidata 的 CC BY-SA 文本做底稿，翻译＋改写＋人工校对；AI 只做初稿，编辑签字；
- 缺失照片的 288 个目的地：要么补授权图，要么先不出页面；
- 保留现在「不编造历史」的原则，但把「暂无介绍」换成「我们正在核对，先看这 8 个可执行的建议」。

### 3. 让内容可被抓取：给每个目的地一个真正的 URL

- 新增服务端渲染路由：`/guide/:slug`、`/country/:code`、`/route/:slug`、`/city/:slug`；
- 每页独立 `<title>`、description、canonical、OG、`Article`/`ItemList`/`BreadcrumbList`/`FAQPage` 结构化数据；
- 内链全部用 `<a href>`（现在探索页一个都没有），面包屑回到国家/大洲；
- 生成 **分片 sitemap**（destinations / routes / countries），只收录达到质量门槛的页面：≥2 张图、≥250 字、≥1 个来源、有更新时间；
- `hreflang` 做 zh-CN / en，英文页用现有的 `name_en` 与英文正文；
- 提交 Google Search Console 与 Bing；面向国内再加百度站长 + 熊掌号（注意海外主机在境内的速度，必要时香港/新加坡节点）；
- 国内真正的流量入口是 **小红书 / 抖音 / 微信公众号**：把「一篇目的地指南」拆成 3 条笔记 + 1 条视频，落地到对应 `/guide/:slug`，比等自然搜索快得多。

### 4. 转化：把「看」接到「订」和「留下」

- 每个指南段落放 1–2 个真实出口：门票/一日游 → Klook、Trip.com、GetYourGuide；住宿 → Booking/Agoda；境内 → 携程/飞猪；
- 统一话术：「前往 Klook 查看实时价格」——不写死价格，不假装有库存（你们现在就是这么做的，继续保持）；
- 收藏/路线保存后引导注册；再加一个「行程清单发到邮箱」的轻表单（不需要账号），这是最便宜的留存；
- 联盟参数单独记，才能知道哪篇内容赚钱。

### 5. 社区：先有 30 个真人，再谈增长

- 删掉 8 条内测帖（含标题为「1」的），冷启动最忌假内容；
- 自己和朋友先发 30–50 条真实行程：图 + 路线 + 花费 + 一句实话；
- 邀请 20 位创作者（小红书旅行博主）给专属页面与署名；
- 匹配逻辑改成「同目的地 + 同月份 + 同预算」，比现在的「徒步/自驾/城市」标签更能促成同行；
- 上线前先开人工审核与举报（`post-quality.js` 已在本地写好但未上线）。

### 6. 工程与信任：先把 5 MB 砍到 1.5 MB

- 删掉已隐藏的 2.97 MB hero 图和 1.84 MB 头像原图（裁成 96px WebP）；
- 全站图片转 AVIF/WebP，按容器出 `srcset`（探索页的 960px Wikimedia 缩略图改 240–320px）；
- 静态资源上 CDN 长缓存，HTML 保持 `no-cache`；
- Render 免费版会休眠：要么升级付费，要么把静态页放 Cloudflare Pages/Vercel，API 单独部署；
- 加统计（Plausible 或 GA4）+ 错误监控（Sentry）+ Core Web Vitals；
- 买一个自己的域名（`*.onrender.com` 不利于品牌与信任）；
- 页脚补 about / contact / 编辑方针 / 隐私 / 条款；AI 生成图继续标注。

## 三、90 天路线图

| 阶段 | 目标 | 具体交付 |
| --- | --- | --- |
| 第 1–2 周（P0） | 先止血 | 删死图、压图、首页 <1.5 MB；接统计；清理测试帖；修 `/api/routes` 为空；把本地已改好的移动端样式合并上线 |
| 第 3–6 周（P1） | 有可排名的页 | `/guide/:slug` SSR + 50 篇中文指南（中国/日本/泰国）+ sitemap + GSC/Bing + 内链 |
| 第 7–10 周 | 有转化 | 每页 booking 模块 + 邮件清单 + 联盟追踪；50 → 200 篇 |
| 第 11–13 周 | 有留存 | 小红书/抖音账号同步更新；社区 30 条真实内容；创作者计划；月度内容日历 |

## 四、只看四个指标

1. 自然搜索/社媒带来的落地页会话数；
2. 指南页 → 预订出口的点击率（目标 8–15%）；
3. 注册转化率与「保存路线」数；
4. 次周回访率（内容型网站 25%+ 算健康）。

## 五、我可以直接开工的第一批

1. `/guide/:slug` 服务端渲染 + 动态 meta + 分片 sitemap（1–2 天）；
2. 性能清理：首页 5.3 MB → <1.5 MB（半天）；
3. 内容模板 + 先写 10 篇（长城/故宫/西湖/富士山/京都/曼谷/清迈/新加坡/巴黎/罗马）作为标准样例；
4. 统计与错误监控接入（半天）。
